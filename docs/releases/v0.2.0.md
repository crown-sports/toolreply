# toolreply 0.2.0: check saved histories in GitHub Actions

Version 0.2.0 adds a same-repository GitHub Action for regression fixtures. After checking out
your repository, one step checks multiple saved conversations without a package installation
step. Broken call/result lifecycles fail CI; a payload-free JSON report remains available on
failure. Existing CLI lifecycle rules and the CLI JSON report schema are unchanged.

```yaml
- uses: crown-sports/toolreply@v0.2.0
  id: histories
  with:
    files: tests/fixtures/openai/**/*.json
    format: openai-chat
    warnings-as-errors: "true"
```

Use a reviewed release's full commit SHA for an immutable action pin. The complete
[English workflow guide](https://github.com/crown-sports/toolreply/blob/v0.2.0/docs/action.md)
and [中文使用说明](https://github.com/crown-sports/toolreply/blob/v0.2.0/docs/action.zh-CN.md)
cover multiple patterns, optional artifact upload after failure, outputs, and local reproduction.

The action uses official `setup-python`, pinned to a full commit SHA, and Python 3.12. The runner
uses `-I -S` and the action checkout's own source, so consumer modules and `PYTHONPATH` cannot
replace its imports. It reuses the CLI's JSON reader, 16 MiB per-file limit, error handling and
privacy behavior. Python setup may download a runtime; the audit does not make network requests.

Every nonblank file pattern must match; overlapping patterns check each resolved file once.
Absolute paths, parent traversal and symlink targets outside the workspace are rejected. The
format is explicit (`openai-chat` or `anthropic`), and boolean options accept only `true`/`false`.
The action returns `2` for input/configuration errors, `1` for lifecycle errors or strict warnings,
and `0` otherwise. Reports are written to unique temporary directories before this result is returned.

The aggregate report uses `action_schema_version: 1` and retains each CLI report as a nested
`schema_version: 1` object. It contains relative fixture paths and diagnostic locations/counts,
not tool names, IDs, arguments or transcript content. Filenames may themselves be sensitive.
The action never uploads reports automatically; console and job-summary output contain counts only.

This remains an early lifecycle linter: it does not validate the complete provider schema,
execute tools, prove recorded operations occurred, or evaluate answer quality. Files with zero
supported tool calls are explicitly counted and are not evidence of lifecycle coverage.

## Installation and assets

- `toolreply-0.2.0-py3-none-any.whl`: installable CLI/Python API package, without Action files.
- `toolreply-0.2.0.tar.gz`: source distribution including the action, adapter, guides, fixtures and tests.
- `SHA256SUMS`: SHA-256 checksums for these two assets.

The GitHub Action itself is selected through the repository's tag or commit, not by installing
the wheel. The package is not published on PyPI.

```sh
python -m pip install /path/to/toolreply-0.2.0-py3-none-any.whl
toolreply --version
```

The test suite includes isolated consumer-import checks, adversarial filenames, workspace and
symlink boundaries, duplicate/unmatched globs, pending-tail policies, invalid JSON and report
retention on failure. The action smoke workflow calls the action on hosted Ubuntu, Windows and
macOS and asserts expected failure outcomes and report counts; it does not merely ignore errors.
